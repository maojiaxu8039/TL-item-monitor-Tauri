## 1. 业务逻辑全景分析

### 1.1 产品定位

**核心目标**: 帮助火炬之光无限玩家围绕"火价"和"物品火价"做交易判断，实现"数据可信 + 提醒及时 + 建议可解释"。

**目标用户**: 火炬之光无限游戏玩家，特别是关注游戏经济系统的玩家。

**核心价值主张**:
- 实时掌握火价走势，判断最佳买卖时机
- 监控关注物品价格，发现捡漏/出货机会
- 基于历史数据的价格分析和预测
- AI 辅助决策，提供个性化建议

### 1.2 核心业务实体

| 实体 | 表/结构 | 业务意义 | 当前状态 |
|------|---------|----------|----------|
| 赛季 | `seasons` | 区分 `ss12/ss11/ss10` 等数据域 | ✅ 已seed |
| 市场模式 | `market_mode` | 区分 `season_normal` 普通服和 `season_expert` 专家服 | ✅ 已隔离 |
| 当前物品价格 | `items` | 当前赛季/模式下物品最新火价 | ✅ 可用 |
| 火价历史 | `fire_price_records` | RMB 与火的兑换价历史（按 season/mode 隔离） | ✅ 可用 |
| 物品价格快照 | `item_price_snapshots` | 物品历史价格，用于趋势、对比、捡漏 | ✅ 可用 |
| 分组 | `sections` | 用户关注列表的分组容器 | ✅ 可用 |
| 分组物品 | `section_items` | 用户关注的具体物品、目标买入价、数量、more 值 | ✅ 可用 |
| 策略 | `strategies` | 评估/排序/通知策略 | ⚠️ 未接入 |
| 告警规则 | `alert_rules` | 用户自定义阈值规则 | ⚠️ 未接入后台 |
| 告警事件 | `alert_events` | 告警记录 | ⚠️ 基本不产生 |
| 源诊断 | `source_diagnostics` | 记录 API/本地文件抓取成功失败状态 | ✅ 可用 |
| 应用配置 | YAML `AppConfig` | 抓取、桌面、通知、数据保留、赛季配置 | ✅ 可用 |

### 1.3 数据流闭环

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  数据采集    │────▶│  数据存储    │────▶│  数据分析    │
│ (Scraper)   │     │ (SQLite)    │     │ (Analysis)  │
└─────────────┘     └─────────────┘     └──────┬──────┘
       ▲                                         │
       │                                         ▼
       │                                  ┌─────────────┐
       │                                  │  用户决策    │
       │                                  │ (Decision)  │
       │                                  └──────┬──────┘
       │                                         │
       └─────────────────────────────────────────┘
                    (反馈循环)
```

**当前状态**: 采集 -> 存储 -> 分析 链路已打通，但 告警/通知 链路未完全闭合。

## 3. v2.5 开发计划

### 3.1 第一阶段：业务闭环 (P0 - 2周)

**目标**: 让"采集 -> 存储 -> 分析 -> 通知"完全闭环

| 序号 | 功能 | 工时 | 依赖 | 验收标准 |
|------|------|------|------|----------|
| 1 | 预警规则接入后台任务 | 3天 | alert_task.rs | 后台按alert_rules触发，写alert_events |
| 2 | 预警Cooldown机制 | 2天 | #1 | 同一规则60秒内不重复触发 |
| 3 | 整赛季火价同步 | 2天 | server.rs | /fire-history-all路由可用 |
| 4 | DataMonitor分页同步 | 2天 | #3 | 大数据量分页同步不超时 |
| 5 | 设置页Patch模式保存 | 1天 | SettingsPage.tsx | 保存时不覆盖其他配置 |

**业务价值**: 用户配置的预警规则真正生效，数据监控可以同步完整赛季数据。

### 3.2 第二阶段：体验优化 (P1 - 2周)

**目标**: 提升数据可信度和用户体验

| 序号 | 功能 | 工时 | 依赖 | 验收标准 |
|------|------|------|------|----------|
| 6 | 捡漏算法基线优化 | 3天 | deals.rs | 支持1h/24h/7d三种基线 |
| 7 | 物价分析接入真实数据 | 3天 | PriceAnalysisPage.tsx | 消除所有mock数据 |
| 8 | 历史任务第一条快照延迟 | 2天 | history_task.rs | 启动后立即写第一条快照 |
| 9 | Dashboard资产指标拆分 | 2天 | DashboardStats.tsx | 投入/当前/浮盈/折RMB |
| 10 | 数据时间显示 | 1天 | 所有分析页面 | 显示数据时间和样本数 |

**业务价值**: 分析建议基于真实数据，用户知道数据新鲜度和可信度。

### 3.3 第三阶段：新功能开发 (P2 - 3周)

**目标**: 开发识图助手和策略管理

## 6. 风险评估

### 6.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| OCR识别准确率低 | 中 | 高 | 选用成熟OCR库，提供人工修正 |
| 历史数据不足 | 高 | 中 | 引导用户开启自动采集，提供数据导入 |
| 第三方API变更 | 中 | 高 | 抽象API层，快速切换源 |

### 6.2 业务风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 分析建议误导用户 | 中 | 高 | 添加免责声明，显示数据时间 |
| 预警过于频繁 | 中 | 中 | Cooldown机制，Quiet Hours |
| 专家服数据不准确 | 低 | 高 | 模式隔离，数据来源标记 |
